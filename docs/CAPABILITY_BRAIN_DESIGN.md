ENGINE-AGNOSTIC CAPABILITY + SHARED BRAIN ARCHITECTURE - design (deliverable for Marek)

DESIGN SUMMARY
One brain, one registry, N thin adapters, one proof. The unit of the system is a CAPABILITY: a declared cbox feature with an enforcement class, a payload source, and a per-engine delivery binding. Capabilities are declared once in a new `etc/capabilities/capabilities.json` (sibling of the three registries that already exist: `etc/registry/settings.json` knobs, `etc/engines/engines.json` engine facts, `etc/mcp/delegates.json` tools). Engines never get features coded ad-hoc; they get adapters - thin per-engine transports with a fixed contract - and the parity between what the registry declares and what each engine's GENERATED ARTIFACTS carry is proved by extending the existing context-manifest digest mechanism (generators.sh:2820-2900, doctor row "context-manifest"). Precise claim (sol re-review): the digest proves generated-artifact parity on disk - it does NOT by itself prove installed mounts, hook execution, or runtime receipt by a live engine; those remain verified by the boot preflights and doctor rows, not by the manifest. The shared brain is NOT one capability among others: it is the data layer underneath, engine-agnostic by construction (files on disk), and capabilities are the delivery/enforcement layer that gives any client access to it. The red line holds by placement, not promise: a HARD security invariant is only ever enforced in the two engine-blind planes (substrate and mediated tools), so an engine that lacks hooks can never silently lose a guard - it either never had the dangerous ability, or the dependent feature is off with a doctor row. This is buildable because the tree already contains every load-bearing precedent: the shim already enforces guards server-side for any caller and injects the kernel (codex_mcp_shim.py:412-450), one loader already serves two engines' brain injection (continuity_session_start.py via claude SessionStart and codex hooks.json), and the manifest digest idiom already proves context parity.

CORRECTION TO THE INPUT SCAN (empirical, changes the matrix): both non-claude engines have grown upstream hook systems since the 07-31 ledger note. Codex CLI ships an experimental hooks engine (v0.114+, behind `[features].codex_hooks = true`): PreToolUse/PostToolUse exist but PreToolUse intercepts ONLY the Bash tool (no file-write, no MCP-call interception), can only deny, and PostToolUse is observe-only (corroborated by openai/codex issues #18491 and #14754 - both are open feature requests to extend beyond Bash). Hermes Agent ships shell hooks declared in config.yaml `hooks:` with claude-like shape (matcher/command/timeout, JSON payload on stdin with hook_event_name/tool_name/tool_input/session_id/cwd), events mirroring plugin events including `pre_tool_call` (CAN block via stdout JSON `{"decision":"block","reason":...}`), `post_tool_call`, `pre_llm_call`, session lifecycle - with two sharp caveats: non-zero exit and malformed JSON DO NOT block (fail-open on crash), and the first-use consent allowlist keys on the command STRING, not the script hash (editing the script does not invalidate consent). All of this is third-party/upstream documentation: whether the PINNED versions in cbox (CBOX_CODEX_VERSION, CBOX_HERMES_VERSION) carry these features and with exactly these semantics is a host experiment, and both guard increments below stay gated behind it with bump tripwires. The honest problem statement is therefore no longer "hermes has nothing, physics forbids it" - it is "three hook dialects with different coverage, blocking semantics, crash behavior, and trust models, plus future clients that may have nothing." That is exactly the problem a registry + adapters + proof architecture is for, and it is NOT a problem one mechanism can solve.

1. THE THREE PLANES - what is physically engine-agnostic and what is not

Every cbox delivery mechanism in the tree today lands in one of three planes. The planes are the physical truth of the design; capabilities declare which plane(s) they use, and the red line is a placement rule over them.

P1 SUBSTRATE (engine-blind, works for any client including future ones, because it needs zero engine cooperation):
- container boundary + mounts: `:ro` binds for hooks/agents/managed-settings (generators.sh mounts region), user layer `:ro`, egress proxy/SOCKS + allowlists, no docker socket;
- entrypoint argv pinning: codex always runs `--strict-config --profile cbox-container --dangerously-bypass-hook-trust` and rejects `-p/--profile` overrides (entrypoint.sh:635-645); hermes always gets the composed ephemeral system prompt (entrypoint.sh:704-710);
- boot gates: claude refuses to start if any codex-* NAMED MCP entry is not shim-wrapped (_check_codex_mcp_shim_seed, entrypoint.sh:190-261) - [LIVE GAP in landed code] the gate matches by name-prefix/adapter-label ONLY, not by resolving the entry's command+args, so a user stdio entry named innocuously with command ["codex","mcp-server"] bypasses shim-wrap entirely and renders RAW: an unshimmed codex mcp-server with none of the cwd-scope/git/depth/kernel-injection guards (see section 5 for the required fix); codex refuses to start on a present-but-unparseable-or-writable hooks.json, or a missing/unparseable profile (_codex_profile_preflight, entrypoint.sh:338-379) - [LIVE GAP in landed code] two preflight gaps remain: profile WRITABILITY is never checked (only existence/non-empty/TOML-parse), and a MISSING or EMPTY hooks.json is silently ACCEPTED (the writability/parse checks run only inside the [ -e ] && [ -s ] guard), so these are open hardening items, not the closed boot gate implied;
- tmux session wrapper: _multiplex_run (entrypoint.sh:308-336) wraps ANY engine; the safeguard watchdog and limit autoresume ride on it;
- host/hub side: cbox dispatcher, session store, bridge, watchdog reconciler.

P2 MEDIATED TOOLS (engine-agnostic through the one cross-engine STANDARD, MCP): cbox-owned MCP servers are enforcement points that work identically for every caller. This is already real, not aspirational: codex_mcp_shim.py enforces cwd-scope + git-worktree (check_cwd_scope_and_git :176-208, deny + audit), rejects caller-supplied instruction keys (:428-432, :440-444), pins model/effort (:433, :445), pins approval-policy=never + sandbox=danger-full-access in-container (:446-448), injects the conduct kernel as developer-instructions into EVERY delegate call (:449), sets child depth env (:375-378) and disables the tool entirely at depth (:502). hermes_delegate_mcp.py enforces depth (:67-68, :676-679), a flock concurrency semaphore (:103-145), and audits (:188). Whoever the caller is - claude, hermes, a future client - these guards hold. The claude-side codex_mode_guard PreToolUse hook is defense-in-depth on top, not the enforcement.

P3 ENGINE-NATIVE (per-engine, never unifiable as a mechanism - only as a source):
- context channels: claude CLAUDE.md kernel block + SessionStart hook payloads; codex AGENTS.override.md render (gen_codex_agents_into, generators.sh:2640-2724, 64000-byte cap) + hooks.json SessionStart; hermes ephemeral system prompt composed in the entrypoint (:591-615, user-policy cap 16384);
- native hook engines: claude settings.json hooks (rich event set, deny-union, managed-settings :ro mirror for four guards); codex hooks.json (today rendered with SessionStart only, gen_codex_hooks_json_into generators.sh:2562-2585; upstream experimental per-tool events per the correction above); hermes config.yaml shell hooks (upstream, unverified in pin);
- native config formats: settings.json / config.toml / config.yaml - and their write idioms (merge_settings_json union, marker blocks, block-replace _hermes_apply_mcp_servers entrypoint.sh:461-523).

The honest theorem of the design: P1 and P2 are engine-agnostic BY CONSTRUCTION; P3 is engine-specific FOREVER. Therefore: hard invariants go to P1/P2 only; text and behavioral features have one SOURCE and N P3 transports; and the unification you can prove is "one source + N adapters + digest parity," never "one mechanism."

2. CAPABILITY ABSTRACTION

A capability is: id, class, enforcement, payload source(s), audience, per-engine binding, degradation policy. The classes, with the census of what exists today:

(a) CONTEXT - passive rules text. Sources: etc/hooks/conduct-kernel.txt (audience: everyone including delegates), etc/hooks/session-core.txt (audience: main drivers only), etc/hooks/orchestrator-global.txt, user policies. Engine-agnostic as SOURCE; delivery is P3 per engine plus one P2 surprise that already exists: the shim injects the kernel into codex delegate calls (codex_mcp_shim.py:449), and hermes-delegate deliberately does not (--ignore-rules, :594 - owner decision 3 of USER_EXTENSION_DESIGN).
(b) GUARDS - active blocking. Two sub-classes with different physics:
  (b1) HARD invariants (must never be lost): delegation depth, cwd scope, codex's own sandbox/approval-policy pin, shim-wrap of codex servers (satisfied for name-labeled entries only; argv-resolution gap open, see section 1 boot gates and section 5), hooks-config tamper resistance, egress policy. ALL of these are already enforced in P1/P2 (census above), with the one open exception noted inline (shim-wrap argv-resolution gap). None of them depends on a client hook. This is the red line satisfied by construction where the P2 fix above is applied, and the design makes it law: a b1 guard MAY have a P3 hook as defense-in-depth but MUST have its enforcement in P1/P2, or the dependent feature does not render for that engine.
  (b2) BEHAVIORAL guards (protect the human's conventions, not the sandbox): commit_guard, rm_glob_guard, code_hygiene_guard, agent_label_guard, spawn_gate, claude permission_mode/plan-mode gating (codex_mode_guard.py) - today claude-only via settings.merge.json PreToolUse (six matchers) with four mirrored into managed-settings.merge.json (:ro); permission_mode/plan-mode is claude CLI session state, does NOT propagate to hermes/bare-codex callers. These CAN be lost per-engine without a security hole; losing them silently is still forbidden (degradation policy below).
(c) OBSERVABILITY - PostToolUse enrichment and mechanical logging: continuity_commit_log (Bash), continuity_ledger_sweep (Edit|Write), continuity_session_digest (SessionEnd), devel_explain.py (the DEVEL explainer; [LIVE GAP in landed code, corrected anchor] NOT present in etc/hooks - only a stale __pycache__ artifact remains there; the source is an uncommitted scratchpad draft per PROGRESS_2026_08_07.md, wired nowhere - not in settings.merge.json, not in gen_hooks_dir - i.e. pre-wave, not mid-wave). Claude-native today. The engine-agnostic FLOOR for this class already exists and is load-bearing: post-hoc mining of the engine's own history store via cbox_session_bridge.py (claude-jsonl, codex-jsonl, hermes-sqlite - engines.json history_read). Inline-vs-mined is a fidelity difference, not a feature difference.
(d) TOOLS/MCP - delegates and utility tools. Already the most unified layer in the tree: delegates.json entries with `_cbox {adapter, available_to, backend, side_effects, enabled_when_env}` rendered through one chokepoint _cbox_render_mcp_for_target (generators.sh:254; call sites :2126 hermes, :2193/:2300 claude, :2476 codex) into three native formats. This layer is the TEMPLATE the rest of the design generalizes.
(e) LIFECYCLE - session multiplex, safeguard autoconfirm, limit autoresume, scope farm, login bridges, cross-engine handoff. Mostly P1 (tmux wrapper, entrypoint, watchdog) = engine-agnostic by construction; per-engine facts are already declared in engines.json (resume_argv, preassign_id, login, probe, history_read, seed_channel).

Per-class verdict on "realne engine-agnosticke?": (d) yes at the protocol level (MCP is the only standard all clients speak); (e) yes at the process level (tmux/entrypoint see every engine the same); (b1) yes because it never needed the engine; (a) source yes / transport no; (b2) no - native hook dialects, forever per-engine, adapter-normalized at best; (c) inline no / mined yes.

3. THE BRAIN - the data layer under capabilities (task items 7 and 9)

Answer to 7: the brain is NOT a capability in the registry; it is the LAYER BELOW. Capabilities are verbs (inject, log, guard, hand off); the brain is the noun they act on. Concretely the brain is already engine-agnostic by construction because it is plain files in the project tree, chosen deliberately over any engine's private store:

- STATE (what is live now; high churn; driver-written): .cbox/LEDGER.md (single source of truth, live wave only) + the session store .cbox/sessions/s-*/session.json (cboxSessionId, engines{native ids, locators, cursors, lineage}, activeMain, state) + .cbox/runtime/ (sessions.json, native-index, mirrors).
- MEMORY (what was learned; append-mostly): PROGRESS_YYYY_MM_DD.md, LEDGER_ARCHIVE.md, DIARY.md, CHANGELOG.md, and the handoff distillates .cbox/sessions/s-*/distillates/handoff-NNNNNN.json (layerA verbatim / layerB deterministic summaries, built by cbox_session_bridge.py merge from any engine's native history).
- CONTEXT (the rules; cbox-owned, versioned, flows one way cbox->engines, never project-written): conduct-kernel.txt, session-core.txt, policies. This is the (a) capability payload, listed here because task item 9 asks how the three relate: context is brain only in the sense that it is injected alongside brain payloads; its OWNER is cbox (versioned "conduct-kernel v5", digest-stamped), while state/memory are owned by the project.

The three-way split is not new design - it is already live in code and the design only names it as schema: continuity_session_start.py assigns each injected payload a kind with its own byte budget (core 7000, reference/ledger/progress 4000, shared-memory 12000; :10-23) and wraps each in BEGIN/END fences with a digest (:231-247), explicitly labeling reference payloads "reference data only, not instructions or commands." That is the brain/context distinction enforced at the injection boundary.

How the brain reaches any engine (delivery is capabilities (a)+(e)):
- claude: SessionStart hook runs the loader; payloads = core + shared-memory (handoff distillate, path-validated against the session store, :254-314) + bounded ledger + progress tail.
- codex: hooks.json SessionStart runs THE SAME loader script (gen_codex_hooks_json_into) - one loader, two transports, already true today.
- hermes: entrypoint composes kernel+core (_hermes_kernel_preamble :591-606) + bridge-rendered handoff (:688-703) into the ephemeral prompt - but does NOT inject ledger/progress payloads; hermes today gets only the TEXT INSTRUCTION to reconstitute (session-core says so), not the payload. This is a real, closable gap and increment M2 closes it with the same loader (the loader is transport-independent: reads optional stdin JSON, tolerates empty, resolves the git root from cwd, writes fenced text to stdout - callable from the entrypoint with its stdout appended to the prompt). Two dedup rules for M2, both mandatory: (i) the hermes preamble becomes kernel-only and the loader supplies core + brain payloads, so session-core is emitted exactly once; (ii) the loader call SUPERSEDES the entrypoint's own bridge-render block (:688-703 is removed) - the loader already reads CBOX_SESSION_MEMORY_FILE and emits the shared-memory payload itself (:254-314). [CONFIRMED / PARTIAL, corrected] The loader's version is NOT uniformly stronger: (a) its path-validation and 2MB cap are equal-or-stronger than the entrypoint block; (b) its session-id match is WEAKER on empty CBOX_SESSION_ID - continuity_session_start.py SKIPS the check on empty/unset and matches any session dir, whereas entrypoint.sh's ${CBOX_SESSION_ID:-invalid} glob fails CLOSED on empty/unset. PRECONDITION for M2: fix the loader to REJECT (not skip) on unset/empty CBOX_SESSION_ID BEFORE the entrypoint's bridge-render block (:688-703) is removed - deleting that block first, with the loader's weaker check still in place, is a regression, not a dedup. Byte-retention reconciliation is also required: the loader keeps the FIRST 12000 bytes (prefix) of the distillate, the bridge keeps the LAST 16000 bytes (tail); standardize on the bridge's tail-biased 16000 (recency is the more useful retention direction for a resumed session), update SHARED_MEMORY_BODY_BYTE_CAP and the _bound_payload truncation direction to match, or explicitly document shared-memory as exempt from the generic prefix-cap convention if the two are kept deliberately different.
- any future client: whatever its start-text channel is, the adapter calls the same loader and pipes the output into it. The loader is the brain's one renderer; transports multiply, the renderer does not.

4. WRITE DISCIPLINE - who writes the brain when everything is engine-agnostic (task items 8 and 10)

The existing invariant scales cleanly once it is stated as ROLES, not engines. Three writer roles, all already present in the tree:

- w1 DRIVER (free-form writes to the .md brain): exactly one human-driven session at a time, whichever engine it runs on. ONE-ACTIVE-WRITER is an invariant, not a lock (session-core.txt states "do not add file locking" - ruling). The session store already models it: session.json activeMain/state; the hub (tmux owner per the 07-31 ruling "conduct jadro = cbox hub") is the natural place to KNOW who the active driver is. [LIVE GAP in landed code] Doctor does NOT yet surface a multi-activeMain violation as a row: the current lease check (cbox-session.sh:624, _cbox_session_field_get) checks activeMain only WITHIN a single session id; two different live session ids in the same project scope can each independently hold activeMain with no cross-sid detection anywhere in the tree today. See the M1-addendum in section 8 for the required scan.
- w2 CBOX MECHANICS (deterministic, provenance-stamped, bounded appends): the continuity hooks already write CHANGELOG/PROGRESS mechanically on claude (commit log, ledger sweep, session digest); the bridge writes session.json and distillates; the watchdog writes runtime state. These are infrastructure writers, NOT delegates, and they are allowed because their writes are mechanical (derived from observed events, no judgment). Per-engine today: claude full (PostToolUse+SessionEnd), codex none (SessionStart only - the policy text "without hooks, keep the old manual discipline" covers it), hermes none. Degradation for w2 is class (c): where inline hooks are missing, records can be MINED post-hoc from the native history store by the bridge - but [CONFIRMED, partial] mined records today are chat text ONLY (user/assistant turns); none of the extractors (extract_claude/extract_codex/extract_hermes in cbox_session_bridge.py) capture commit/edit/tool-outcome events. This is lower FIDELITY, NOT equal durability. Hermes is further constrained: its sqlite messages table (id/role/content/timestamp) has no event-type column, so those events may be unminable at the source even if the extractor were extended.
- w3 DELEGATES AND TOOLS: never write the brain. Return a distillate; the driver decides durability. [LIVE GAP in landed code, corrected strength] Enforced today by text (kernel DELEGATE WRITE BOUNDARY) ONLY; for hermes-delegate the ephemeral HOME/cwd (tempfile.mkdtemp + --ignore-rules, hermes_delegate_mcp.py:568-601) is a default-location convenience, NOT a write barrier - PATH is inherited and absolute-path writes to the real project tree are not blocked. This is text-governed like engine-native subagents, and belongs in section 10 (WHAT CANNOT BE UNIFIED), not implied as substrate-enforced.

Per-file-class write matrix (the sharpening the scale-out needs):
- LEDGER.md, OPEN_QUESTIONS.md, DIARY.md: w1 only.
- PROGRESS_*.md, CHANGELOG.md: w1 free-form + w2 mechanical appends (both already true).
- .cbox/sessions/**, .cbox/runtime/**: w2 ONLY (hub/bridge/watchdog owned, JSON, O_NOFOLLOW discipline) - this store is OUTSIDE the ONE-ACTIVE-WRITER invariant, which governs the human-facing .md brain, not the machine store.
- generated context (kernel/core renders): cbox regen only; never written from inside a session.

Task item 10, non-conversational tools: their contract is READ freely (the brain is plain files; a script or MCP server reads LEDGER.md or calls `cbox_session_bridge.py render` like the entrypoint does), WRITE only as w2 if the tool is cbox infrastructure (then it must stamp provenance and be append-bounded), else w3 (return data, do not write). Concurrency answer for w1 stays social/structural (one human, hub-visible); for w2 the writers are single-purpose per file (commit log appends CHANGELOG, bridge owns sessions/) so there is no cross-writer contention by design; where a mediated funnel would help future tooling, `cbox brain append` as a CLI verb is listed as an owner decision (a funnel with provenance, compatible with the no-locking ruling, NOT a lock).

5. CAPABILITY REGISTRY - one declarative source of truth + proof

File: etc/capabilities/capabilities.json + a validator etc/capabilities/capability_registry.py in the exact idiom of engines_registry.py (load/validate/names/get, RegistryError, closed key sets). Schema:

{
  "schema": 1,
  "capabilities": {
    "<id>": {
      "class": "context|guard|observe|tool|lifecycle",
      "enforcement": "hard|behavioral|advisory",
      "audience": "all|driver|delegate",
      "sources": ["etc/hooks/conduct-kernel.txt", ...],
      "enabled_when_env": ["CBOX_...", ...] | null,    // referential, AND-of-nonempty: knob(s) LIVE in etc/registry/settings.json, never duplicated here.
                                                        // list form covers compound prerequisites in scope for M1, e.g. local-qwen needs
                                                        // [CBOX_LOCAL_MODEL_URL, CBOX_LOCAL_MODEL_NAME], hermes-local needs the enable flag
                                                        // AND provider AND (base_url when provider==local). The provider==local-implies-
                                                        // base_url conditional is a richer predicate than flat AND and stays a runtime
                                                        // check in hermes_delegate_mcp.py _apply_config - documented here, not silently
                                                        // assumed to be covered by the compound gate.
      "planes": ["substrate", "mediated", "native"],  // where enforcement/delivery actually happens
      "bindings": {
        "claude":  {"mechanism": "settings-hook:PreToolUse", "matcher": "Bash", "artifact": "...", "status": "live"},
        "codex":   {"mechanism": "hooks-json:PreToolUse", "status": "gated:codex-hooks-experiment"},
        "hermes":  {"mechanism": "config-shell-hook:pre_tool_call", "status": "gated:hermes-hooks-experiment"}
      },
      "degrade_floor": "advisory-text|mine-history|feature-off|block-start|none"
    }
  }
}

Degradation precedence, stated once: `degrade_floor` is capability-level (what an engine WITHOUT a live binding gets); a per-engine binding `status` overrides the floor for that engine only. There is no second per-binding degrade field - one knob, one override.

Ownership boundaries against registry proliferation (the conf_save-vs-whitelist lesson, stated as law):
- settings.json owns KNOBS (what the user can set). capabilities.json references them by env name(s), plural - list form for compound prerequisites (`enabled_when_env` - precedent already in delegates.json).
- engines.json owns ENGINE FACTS (probe, versions, channels). capabilities.json references engines by name; a binding for an engine not in engines.json is a validation error. Precedence stated once, here, for the whole design: engines.json is the SOLE owner of engine facts; the adapter's describe() (section 6) is a validation/consumption function that reads and cross-checks engines.json, never a second source that independently declares a fact engines.json lacks. If describe() would need a field with no engines.json counterpart, that is a registry gap to fix in engines.json, not a second source of truth.
- delegates.json owns TOOL ENTRIES (it IS the class-(d) sub-registry; each entry maps to exactly one tool-class capability; `available_to` remains where it is).
- capabilities.json owns the FEATURE-to-DELIVERY mapping and nothing else.
Referential integrity is a test, not a convention: a new lib/test_capabilities_registry.sh asserts (1) every binding engine exists in engines.json, (2) every enabled_when_env entry - iterating the list/compound form - exists in settings.json variables, (3) every delegates.json entry has its tool capability, (4) every hook command in settings.merge.json / managed-settings.merge.json / generated codex hooks.json / rendered hermes hooks block appears in some capability binding, (5) every hardcoded dispatch site in the section-6 inventory matches its APPLICABLE engine subset - PROJECTION-AWARE, not a flat exact-mirror: the unconditional ADMISSION/DISPATCH/CLI/PER-TOOL sites compare against the full engine set; the HISTORY sites (bridge extract, engines_registry HISTORY_READ_VALUES) compare only against engines with history_read != none; the INSTALLER/COMPOSE sites (generators _cbox_bins_volume, cbox-setup channel list, compose bins-volume) compare only against engines with install=bins-volume - so an ad-hoc, registry-invisible delivery, or a new engine missing one of the bounded core edits it is subject to, FAILS CI, while an engine legitimately absent from a projected site (e.g. a history_read:none engine not in the extract dispatch) does NOT false-fail. That last assertion is what makes the registry the single source of truth mechanically rather than by discipline.

Parity proof: generalize the existing context manifest into a capability manifest. Today _cbox_context_manifest_write digests 8 fixed artifacts (kernel, core, claude_md source, loader, codex agents render, shim, settings merge, hermes entrypoint) with a doctor row. The generalization: regen_all (generators.sh:2966) walks capabilities.json and emits generated/capability-manifest.json = {capability x engine -> {mechanism, artifact digest, status}}; _cbox_context_manifest_verify becomes the per-binding drift check; doctor renders the matrix (section 7) from this file. The digest vocabulary and the verify loop already exist - this is a widening, not a new mechanism. The existing context-manifest keys stay as-is during migration (M1 emits both; M3 folds).

Required P2 fix (closes the [LIVE GAP in landed code] at section 1 boot gates): validate_user_entry in render_mcp.py must resolve a user stdio-mcp entry's command+args (not just its declared name/label) and REJECT any entry whose resolved executable+argv is, or invokes, "codex mcp-server" - the entry must go through the shim-wrap path or be refused at render time. This closes the argv-resolution escape; the design here only specifies the required behavior, the code change itself is a separate owner-approved implementation step.

6. ADAPTER CONTRACT - thin per-engine transports

An adapter is one Python module per engine (python-first per the 08-07 ruling; generators.sh call sites keep calling during migration), etc/adapters/<engine>.py, with this fixed surface:

- describe() -> the engine's CHANNEL FACTS, validated against engines.json (engines.json is the sole owner of engine facts, per section 5; describe() never independently declares a fact engines.json lacks): which context channel (seed_channel enum already in engines.json: sessionstart-hook | pointer-prompt | ephemeral-system-prompt), byte budgets (claude payload caps; codex 64000 AGENTS cap; hermes 16384 user-policy cap), hook dialect if any (event names, payload shape, block mechanism, crash semantics fail-open/fail-safe, layering union/replace, trust model), config write idiom (merge-union / marker-block / block-replace / full-file).
- render_context(sources, audience, profile) -> engine-native artifact(s). Claude: CLAUDE.md kernel block + settings hooks entry for the loader. Codex: AGENTS.override.md + hooks.json SessionStart. Hermes: kernel-only preamble + entrypoint loader call.
- render_tools(delegates, target) -> native MCP config. Already exists as _cbox_render_mcp_for_target target branches; the adapter absorbs its per-engine arm.
- render_guards(capabilities) -> native hook config for b2 guards the engine supports, or a DECLINE with reason (feeds the manifest status). MANDATORY: golden payload fixtures per (guard x dialect) - a guard is only "live" on an engine when a recorded native payload fixture drives the actual guard script to a DENY in tests (lib/test_rm_glob_guard.py idiom, extended per dialect). A dialect mismatch otherwise means the guard silently never fires - fail-open disaster with a green render.

7. DEGRADATION - matrix and the red line

The degradation vocabulary is derived from behaviors already in the tree, not invented: block-start (claude refuses to launch on unwrapped codex servers, entrypoint.sh:190-261), enforce-substrate (argv pinning, :ro mounts, boot preflights), enforce-mediated (shim/delegate server-side checks), enforce-native (claude hooks), advisory-text (kernel/core sentences), mine-history (bridge), feature-off (enabled_when_env gates), plus doctor-row visibility for every non-native state. 10. WHAT CANNOT BE UNIFIED (the honest list)

- One delivery mechanism. Three context channels with different multiplication semantics (claude CLAUDE.md imports multiply per spawn; codex AGENTS is a single 64000-byte file; hermes is a per-process env prompt capped by prompt budget) and three hook dialects. Unifiable: source, renderer, proof. Not unifiable: the transport.
- In-band interception of engine-NATIVE tools on an engine without a hook API (or outside its coverage: codex non-Bash tools today). Physics: the engine's own file/exec tools run inside its process; without a callback there is no seam. The substrate can constrain WHAT is reachable (mounts, egress, argv), never WHICH native call happens.
- Engine-native subagent governance (agent_label_guard, spawn_gate) on engines whose spawn concept differs or is absent - codex has no Agent tool (its analog is the MCP delegate path, which IS guarded, in P2); hermes subagents fire only observe events upstream.
- Delegate write-boundary (w3) as a mechanical guarantee - text-governed for engine-native subagents (their file tools are legitimate and indistinguishable in P1) AND, per the corrected anchor in section 4, for hermes-delegate too: its ephemeral HOME/cwd is a convenience default, not an enforced write barrier (PATH inherited, absolute-path writes to the real project tree not blocked).
- One writer mechanism for the brain: w1 stays a social invariant by explicit ruling (no locks); the design surfaces violations (hub/doctor) instead of preventing them.
- Live TUI injection: [corrected anchor] cbox ALREADY pushes text via tmux send-keys today (limit_watchdog.py inject(): resume prompt + Enter; safeguard_confirm(): bare Enter) - the claim that text cannot be pushed into a running session is false. The real constraint is that in-band send-keys is an UNTRUSTED best-effort side channel: it races the input loop and cannot carry authenticated startup context. STRUCTURED context (kernel/hooks/MCP defs) remains next-session (re-render + restart) - that stays the change-propagation model for CAPABILITY content; regen + manifest + doctor governs that structured path, not the send-keys side channel.
- The consent/trust models of the three hook engines (claude deny-union + managed :ro, codex trust-bypass flag + writable-preflight, hermes string-keyed consent + auto-accept) - normalized only as the adapter LAW pattern (bypass requires unwritable source), never as one model.
